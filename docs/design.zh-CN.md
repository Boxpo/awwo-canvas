# 制作思路

AwwO Canvas 的结构，以及每一部分守住的规则。代码是最终依据，这份文档说明它为什么长这样。
English: [design.md](design.md).

## 1. 核心想法

一个目标变成一张小型 Agent 图。每个节点承担一项职责（梳理目标、撰写页面、搭后端、验收交付），
带有类型化的**契约**：需要哪些输入、必须交出哪些输出。连线把输出送到输入，整图按依赖顺序执行；
互审 Graph 会循环，直到评审通过或轮次用完。

让它真正可用而不只是演示的三件事：

1. **画布文档是唯一事实来源**。人和助手都通过同一套经过校验的操作修改它，每次修改都是一步撤销。
2. **编排是数据**。所有提示词都在 `skills/*.md` 里；不属于提示词的规则（路由、团队顺序、互审轮次、重试）都是确定性代码。
3. **执行引擎是可插拔的进程**。编排服务只用一个很小的协议和 worker 通信，不链接任何 Agent SDK，所以引擎可以在运行中接入或离开。

## 2. 画布文档（`packages/core`）

`canvasDoc.ts` 定义一份 JSON 文档：`nodes`、`edges`、`waypoints`、上次的视口 `view`，以及可选的 `execution` 执行策略。

- **节点**分两种：`session`（Agent：角色设定、可选的运行时/模型/思考强度、可选团队、契约）和 `form`（由人填写的标签与值）。
- **契约**（`nodeContracts.ts`）声明输入、输出字段及类型：`text`、`markdown`、`html`、`number`、`boolean`、`file`。
  端口由契约推导（`ports.ts`），只有类型兼容才能连线，单输入只能有一个来源。
- **连线**分 `data`（本轮数据）和 `feedback`（上一轮互审的输出，可以构成跨轮闭环；data 连线不允许成环）。
- **产出如实标注**。节点的 `lastOutput` 记录来源（`run`、`manual`、`case`）以及是否 `partial`（失败运行留下的文本只是证据，不是结果）。
  `invalidateOutputs.ts` 在每次修改后清掉不再成立的旧产出：改节点设置会清掉它和下游；替换产出会清掉下游；
  改线会清掉接收方。只挪位置不清任何东西。

浏览器把文档存在 `localStorage`。读不出来的内容会先备份到单独的键，再允许任何写入，所以一次坏写入不会悄悄变成空画布。

## 3. 规划：封闭协议，两次校验

助手从不直接改画布。规划器返回一份 version 1 协议的**提议**（`canvasPlan.ts`）：11 种操作
（`add_node`、`update_node`、`set_input`、`add_field`、`update_field`、`remove_field`、`remove_node`、
`connect`、`set_edge_kind`、`set_execution`、`disconnect`），未知键直接拒绝，所有尺寸都有硬上限。

1. 画布组装上下文（`planningContext.ts`）：协议、规划指导、7 个角色模板、**当前画布结构**（不含凭证、对话、产物），以及最近几轮对话（仅作意图参考）。
2. 编排服务用 `canvas-planner` skill 发起一次模型调用，流式上报的进度只有测量值（已写字符数、已出现的 `add_node`/`connect` 数、思考长度），
   从不显示百分比，因为没人知道方案最终有多长。
3. 编排服务取出 JSON（允许 ```json 围栏，以及围栏后追加的说明），用与画布**同一个** `parseCanvasPlan` 校验。
4. 画布在私有副本上用 `applyCanvasPlan` 逐条校验引用、类型兼容、单一来源、data 连线成环、互审策略，全部通过才整体替换文档，
   整个方案是**一步**撤销；新增节点自动布局。
5. 方案生成期间画布若被改动（`canvasPlanRevision` 指纹不一致），方案标记为过期，不会覆盖更新的编辑。
6. 结构错误的方案只重试一次；运行时故障和取消不重试，坏模型循环只会白白消耗额度。

## 4. 助手路由：编排还是执行

一个对话处理两类消息（`assistantRoute.ts`、`skills/assistant-router`）：`plan` 调整画布，`execute` 由一个 Agent 立即完成任务。
客户端声明自己能执行哪几种，服务端收窄到已配置的；明确的改画布措辞按规则直接路由，其余询问一个小模型，
判断不了就回落到 **plan**：规划只调用一次、一步撤销，而任务会做实际工作。每条回复都标明走的是哪条路，
也可以一键把最近一条请求改走另一条路。

## 5. 整图运行（`apps/server/src/orchestration`）

运行归编排服务所有，而不是浏览器。

- **准入严格且提前**。运行拿到的是清洗过的文档副本。预检（`runGraph.ts`、`reviewGraph.ts`）检查必填输入、环、互审策略和团队；
  然后**冻结**每个可能执行的节点：对照实时注册表解析运行时和模型，按模型目录校验思考强度，计算上下文预算。任何一项失败，整次运行在第一次模型调用前就被拒绝。
- **冻结就是冻结**。节点准入时的 skill 文本、运行时和模型，就是它执行时用的，即使中途拔掉 worker 或修改 skill。
- **范围运行**只执行选中的节点；范围外的上游提供已保存的产出，标记为 `cached`，不会冒充 `done`。上游没有保存的产出时，
  节点以明确原因阻塞，而不是收到空输入。
- **事件编号**。状态、节点、增量文本、团队发言、轮次、汇总事件组成一份日志；画布按序号跟进，刷新页面或断流后都能精确续上。
- **幂等提交**。每次提交带 `operationId`；重复提交返回同一次运行，拿它提交不同的图会被拒绝。
- **结果写回**在运行结束时只做一次：新产出写进节点，过期的下游被清掉；这次写回作用于所有撤销快照，而不是新增一步编辑，
  所以撤销一次拖动不会把结果一起撤掉。

## 6. 互审 Graph

`execution: { mode: 'review', maxRounds, reviewerNodeId, verdictFieldId }` 把整图变成循环：每轮执行整图，
`feedback` 连线送来上一轮的产出，最终评审节点的布尔判定字段决定结果：`true` 通过，`false` 进入下一轮，轮次上限 1–5。
画布显示当前轮次，汇总说明是通过了还是轮次用尽。

## 7. 节点团队

一个节点可以是 1–8 个成员的团队（`nodeTeam.ts`、`skills/team-orchestration`），确定性执行：顺序、可见范围、何时停止都由编排器决定，不由模型决定。

| 模式 | 顺序与结果 | 计划调用数 |
| --- | --- | --- |
| 顺序接力 | 按顺序各调用一次，最后一位的输出是结果 | N |
| 并行汇总 | 前 N−1 位并行，最后一位汇总；任一失败即停止同组 | N |
| 多轮讨论 | R 轮依次发言，最后一位再总结一次 | N × R + 1 |
| 审核返工 | 前 N−1 位产出/返工，最后一位用严格 JSON 给出判定 | 最多 N × R |

`maxTurns` 是模型调用次数的硬上限，`timeoutSeconds` 是整个团队的时间上限。成员输出只是数据，永远不是指令。团队最终仍按节点的输出契约交付。

## 8. 热插拔执行器

协议（`packages/core/src/protocol.ts`）只有四个端点：`GET /health`、`POST /internal/runs`（事件流）、
`DELETE /internal/runs/{runId}`、`POST /internal/completions`。注册表（`apps/server/src/runtimes/registry.ts`）：

- 读取 `runtimes.json`（监听文件变化），也接受通过 API 注册的执行器，包括启动时自行注册的 worker；
- 探测每个 worker 并校验目录：它上报的运行时 ID 必须与注册 ID 一致，接错地址也不会把调用转到别处；模型声明输入预算（上限 256 KiB）和可用的思考强度；
- worker 地址和 token 只留在编排服务里：浏览器只看到 ID、名称和目录；
- 从不迁移正在进行的调用：运行时在准入时已冻结，被拔掉的 worker 上的调用会明确失败，而不是交给另一个引擎。

worker 只上报思考内容的**字符数**，从不传出思考文本；只返回思考、没有正文的模型以 `reasoning_only_output` 失败，而不是给出空结果。

## 9. Skill 即数据

`skills/<name>/SKILL.md` 由 frontmatter（`name`、`version`、`description`）和命名块（`### block: system` 后接围栏代码块）组成。
`apps/server/src/skills.ts` 负责加载、计算哈希、文件变化时重载；缺少必需的块时拒绝启动。调整提示词就是改文件、像代码一样评审，服务端代码里没有藏任何措辞。

## 10. 这个版本不包含的

账号、计费、AwwO 托管 Agent 与市场、SSO、桌面端外壳和生产部署。相对上游有意做出的改动，见 [NOTICE.md](../NOTICE.md)。
